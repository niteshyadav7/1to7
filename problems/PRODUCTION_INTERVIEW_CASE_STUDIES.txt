CASE 1: The Silent 1,000-Row Clamping Disaster in Supabase PostgREST
====================================================================================================
CATEGORIES: Backend / Supabase / PostgREST / Database Scaling / Pagination
INTERVIEW QUESTION: "Tell me about a high-severity data bug in production that looked like data corruption but was an architectural constraint."

[SITUATION]
Admin complained that creator Sanchita Sanyal (HY10891) had applied to multiple campaigns (Origami, Lavie), but searching for her ID on the main Applications Admin portal returned "No applications found". In the creator's mobile virtual view, her applications were active.

[ROOT CAUSE INVESTIGATION]
1. Audited PostgreSQL direct via SQL: The user and all 5 of her applications existed in the database table `applications`.
2. Total rows in `applications` had recently reached 1,745.
3. The API route `/api/admin/applications` called:
      supabase.from('applications').select(...).order('created_at', { ascending: false })
4. By design, Supabase's PostgREST proxy enforces a strict server-side hard ceiling of `max-rows: 1000`. Even if you do not specify a `.limit()`, PostgREST silently truncates the result set to the first 1,000 records.
5. Sanchita applied to Origami and Lavie on September 22, 2026. Because 1,000 new applications had been created since October 7, her applications were at index ~1,350 in chronological order.
6. PostgREST silently dropped records 1001 through 1745. The frontend never received them.

[SOLUTION & ARCHITECTURE]
1. Implemented Automatic Parallel Chunked Fetching:
   - Step 1: Execute a lightweight `select('*', { count: 'exact', head: true })` to get total row count.
   - Step 2: Compute `chunksNeeded = Math.ceil(totalCount / 1000)`.
   - Step 3: Dispatch parallel queries using `Promise.all` over disjoint ranges:
             `range(0, 999)`, `range(1000, 1999)`, etc.
   - Step 4: Combine the chunk results into a complete, zero-loss collection.
2. Optimized User History Enrichment:
   - In the all-applications view, avoid making secondary `.in('user_id', userIds)` network queries (which also get clamped at 1000). Instead, compute cross-campaign user workload directly from the in-memory combined array.
3. Added Database Performance B-Tree Indexes:
   - `CREATE INDEX idx_applications_created_at ON applications(created_at DESC);`
   - `CREATE INDEX idx_applications_campaign_created ON applications(campaign_id, created_at DESC);`
   - `CREATE INDEX idx_applications_status ON applications(status);`

[INTERVIEW STAR TAKEAWAY]
- Situation: High-traffic app where older records disappeared once table exceeded 1000 rows.
- Task: Identify why data was missing despite existing in PostgreSQL and ensure zero data loss.
- Action: Discovered PostgREST proxy max-rows cap; engineered parallel chunked range queries and added compound indexes.
- Result: 100% data fidelity restored immediately, query executed in <350ms for 1,745+ rows.

CASE 2: PostgreSQL UUID Type-Casting 500 Crash (Dual Slug / UUID Resolution)
====================================================================================================
CATEGORIES: PostgreSQL / API Routing / Data Validation / Next.js
INTERVIEW QUESTION: "How do you handle API parameters that could be either an internal UUID or a human-friendly slug/code without database runtime crashes?"

[SITUATION]
Admin portal provides URLs like `/admin/applications/[campaign_id]`. Admins sometimes clicked links or shared URLs containing the campaign's human-readable code (e.g., `F10024C201` for Origami) instead of its UUID `cbf96c0c-961f-4b50-943d-7c17b47bdd9f`. This threw a 500 Internal Server Error.

[ROOT CAUSE]
PostgreSQL strictly validates types. The route passed the URL parameter directly into `.eq('id', campaign_id)` and `.eq('campaign_id', campaign_id)`.
Because `campaigns.id` and `applications.campaign_id` are typed as `uuid` columns:
   Error: invalid input syntax for type uuid: "F10024C201" (Postgres error code 22P02)
This aborted the query and returned a 500 error, displaying an empty table to the admin.

[SOLUTION & ARCHITECTURE]
1. Implemented Dual Identifier Resolution using UUID Regex:
   ```ts
   const isUuid = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i.test(rawId);
   let campQuery = supabase.from('campaigns').select('id, brand_name, campaign_code, ...');
   if (isUuid) {
     campQuery = campQuery.eq('id', rawId);
   } else {
     campQuery = campQuery.eq('campaign_code', rawId);
   }
   const { data: campaign } = await campQuery.maybeSingle();
   const resolvedCampaignId = campaign ? campaign.id : (isUuid ? rawId : null);
   ```
2. Applied the same pattern to the CSV export streaming route (`/api/admin/campaigns/export`):
   Dynamically bound either `a.campaign_id = $1` or `c.campaign_code = $1` depending on UUID regex validation.
3. Added database index:
   `CREATE INDEX idx_campaigns_code ON campaigns(campaign_code);`

[INTERVIEW STAR TAKEAWAY]
- Key concept: Defensive parameter resolution. Never trust route parameters to be formatted as UUIDs. Always inspect and resolve polymorphic identifiers prior to binding in SQL clauses.

CASE 3: Real-Time Tab Filter Blindspot & Dynamic Cross-Status Search UX
====================================================================================================
CATEGORIES: Frontend Architecture / React / User Experience / State Management
INTERVIEW QUESTION: "How do you prevent 'false negative' search results in applications with tab-based filtering?"

[SITUATION]
Admins reported that creators who applied were not found when searching by Influencer ID or Phone number.
Creators were actually in the database, but admins were looking on the "Applied" tab while the creator was in "Under Process" or "Rejected". The admin concluded "the creator never applied" because the UI returned 0 results.

[ROOT CAUSE]
Frontend applied status filter before search:
   `result = applications.filter(a => a.status === activeStatus).filter(a => matchesSearch(a))`
Because `activeStatus` defaults to `Applied`, any creator in `Rejected` (e.g., Bioderma rejection) was pruned before the search ran.

[SOLUTION & ARCHITECTURE]
1. Built `matchesApplicationSearch(app, query)` utility checking across full name, ID, handle, email, phone, and remarks.
2. Dynamic Tab Badges with Query Awareness:
   - When no search is active: Tabs display total count per status (`Applied (850)`).
   - When a search is active: Tabs dynamically recompute counts strictly for the searched entity:
     e.g., `Applied (1) | Under Process (1) | Rejected (1) | Approved (0)`
3. Cross-Status Intelligence Banner:
   If the currently selected tab yields 0 records but other tabs contain matches:
   Render an alert banner:
   "0 results in 'Applied', but found 2 applicants matching 'HY10891' in other statuses: [View in All (2)] [View in Rejected (1)]"
4. Empty State Action:
   Added a primary button directly inside the empty state: "Search across All Statuses".

[INTERVIEW STAR TAKEAWAY]
- Shows user empathy and enterprise UX thinking: converting an application from an annoying search failure into a proactive status guide.

CASE 4: Creator Ghosting Event Sourcing, Proof Audit Trail & Access Blocking Gatekeeper
====================================================================================================
CATEGORIES: System Design / Event Sourcing / Integrity Controls / State Machine
INTERVIEW QUESTION: "How do you build an abuse prevention and audit system for contract non-compliance?"

[SITUATION]
Influencers applied, received products or advance commercial payouts, and stopped responding ("ghosted" the brand). Admin teams needed a system to mark ghosting, maintain strict evidence, prevent accidental ghosting, and block ghosted users from taking new brand budgets.

[SOLUTION & ARCHITECTURE]
1. Database Schema (`application_ghost_events` table):
   - `id`, `application_id`, `user_id`, `event_type` ('ghosted' | 'unghosted'), `reason`, `evidence_url`, `notes`, `performed_by`, `performed_at`.

   - When any user attempts to apply (`POST /api/campaigns/[id]/apply`), run check:
     `SELECT count(*) FROM applications WHERE user_id = $1 AND is_ghosted = true;`

4. Unghosting Audit Trail:
   - Admins can unghost only by submitting a formal resolution reason (e.g. "Delivered draft after phone follow-up"), keeping full chronological history of both ghost and unghost actions.

CASE 5: Race Condition in Zero-Gap Sequential ID Generation (HY10891 Trigger Engine)
====================================================================================================
CATEGORIES: Database Concurrency / PostgreSQL Triggers / ACID Transactions
INTERVIEW QUESTION: "How do you guarantee strictly sequential, gapless, formatted IDs (like HY10001, HY10002) under concurrent web traffic?"

[SITUATION]
Influencers receive a formatted ID like `HY10891`. When thousands of influencers registered concurrently during marketing campaigns, standard application-level logic:
   `const last = await db.query('SELECT MAX(influencer_seq_num) ...'); const next = last + 1;`
caused duplicate key violations and race conditions (multiple users receiving identical IDs).

[SOLUTION & ARCHITECTURE]
1. Created dedicated PostgreSQL sequence:
   `CREATE SEQUENCE influencer_id_seq START WITH 10001;`
2. Implemented `BEFORE INSERT` Trigger at the database level:
   ```sql
   CREATE OR REPLACE FUNCTION set_influencer_sequential_id()
   RETURNS TRIGGER AS $$
   BEGIN
     IF NEW.influencer_seq_num IS NULL THEN
       NEW.influencer_seq_num := nextval('influencer_id_seq');
       NEW.influencer_id := 'HY' || NEW.influencer_seq_num::text;
     END IF;
     RETURN NEW;
   END;
   $$ LANGUAGE plpgsql;
   ```
3. Guaranteed thread safety: `nextval()` is atomic and non-blocking in Postgres, completely eliminating race conditions.

CASE 6: CSV Export Column Shifting, [object Object] Bug, and UTF-8 BOM Encoding
====================================================================================================
CATEGORIES: Data Serialization / RFC 4180 / Excel Compatibility
INTERVIEW QUESTION: "Why do CSV exports open corrupted or misaligned in Microsoft Excel, and how do you guarantee clean exports for non-ASCII characters?"

[SITUATION]
1. Dynamic questions with commas in user answers caused subsequent fields (e.g., Bank details, Phone numbers) to shift into the wrong Excel columns.
2. Complex JSON fields like shipping addresses rendered as `[object Object]`.
3. Indian Rupee symbol `₹` and Hindi comments displayed as garbled mojibake characters (`â‚¹`, `???`).

[SOLUTION & ARCHITECTURE]
1. RFC 4180 Compliant Sanitization:
   - All text escaped via quotes, internal line breaks converted to ` | `:
     `val.replace(/\r\n|\r|\n/g, ' | ').replace(/"/g, '""')`
2. JSON Stringification:
   - Detect nested objects/arrays (e.g., `shipping_addresses`, `selected_store`) and format them into readable summary strings before export.
3. UTF-8 Byte Order Mark (BOM):
   - Prepend `\uFEFF` to the start of the CSV output buffer:
     `return new NextResponse('\uFEFF' + csvLines.join('\r\n'), { headers: { 'Content-Type': 'text/csv; charset=utf-8' } });`
   - Excel uses the BOM signature to identify UTF-8 rather than defaulting to ANSI/ASCII.

CASE 9: OAuth Code Fragment Sanitization (#_) & Instagram Token Consistency
====================================================================================================
CATEGORIES: OAuth 2.0 / Mobile Browser Quirks / Instagram Graph API
INTERVIEW QUESTION: "Explain a peculiar issue you encountered integrating OAuth 2.0 with social platforms on mobile browsers."

[SITUATION]
Creators logging in via Instagram OAuth from Instagram in-app browsers or Android Chrome had a 30% login failure rate. The backend returned:
   `OAuthException: Invalid verification code format`

[ROOT CAUSE]
Instagram's redirect URI on mobile devices appends `#_` (hash fragment) to the end of the authorization code in the URL:
   `https://1to7media.in/auth/callback?code=AQD123...#_`
When client-side Next.js parsed `searchParams.get('code')`, the string sometimes retained the trailing `#_` fragment, corrupting the token exchange payload.

[SOLUTION & ARCHITECTURE]
1. Sanitized code before backend exchange:
   `const cleanCode = rawCode.replace(/#_$/, '').trim();`
2. Normalized `redirect_uri` to match the exact protocol (`https://`), port, and trailing slash configured in the Meta Developer App dashboard.

CASE 11: High-Scale Platform Analytics & Real-Time Stats Hub (Server-Side SQL Aggregation vs Client Memory Exhaustion)
====================================================================================================
CATEGORIES: Database Optimization / PostgreSQL / API Design / Next.js / Real-Time Analytics
INTERVIEW QUESTION: "How do you design an enterprise-grade analytics dashboard that tracks 35k+ users, financial disbursements, and daily/weekly velocity without overwhelming client memory or database connection pools?"

[SITUATION]
Admin portal needed a centralized "Platform Stats Hub" (/admin/stats) displaying all platform metrics in one place:
1. High-level KPIs (total applications, active campaigns, 32,600+ creators, disbursed payouts vs pending liabilities, completion rates).
2. Day-wise and Week-wise velocity trends (interactive timeline of submissions, completions, and creator onboardings).
3. Application conversion pipeline funnel (Applied -> Under Process -> Approved -> Completed -> Paid).
4. Creator intelligence & demographics (follower tiers Nano/Micro/Mid/Macro, gender split, geographic distribution).
5. Budget model architecture (Barter vs Paid Variable vs Paid Fixed vs Hybrid).

[ROOT CAUSE / ARCHITECTURAL PITFALL]
If an application attempts to load raw records for 32,600+ creators and thousands of applications into frontend browser memory or Node.js memory:
1. PostgREST enforces a 1,000-row silent clamp, resulting in inaccurate sums and missing data.
2. Network payload balloons to 15MB-30MB of JSON, causing noticeable lag and mobile browser tab crashes.
3. Node.js heap spikes when running `.reduce()` or `.filter()` over tens of thousands of raw objects.
4. Database connection exhaustion occurs if multiple uncoordinated queries lock backend workers.

[SOLUTION & ARCHITECTURE]
1. Server-Side Parallel SQL Aggregations:
   - Built a dedicated API route `/api/admin/stats` utilizing PostgreSQL connection pooling (`pg.Pool`).
   - Replaced all raw data transfers with parameterized, indexed SQL aggregation queries executed concurrently via `Promise.all`:
     * `DATE_TRUNC('day', created_at)` and `DATE_TRUNC('week', created_at)` with `GROUP BY` for granular time-series.
     * Conditional counting using `COUNT(CASE WHEN status::text = '...' THEN 1 END)` to compute the entire funnel in a single table pass.
     * `COALESCE(SUM(partial_payment + final_payment), 0)` for financial velocity calculations.
2. Direct Type Safety & Enum Handling:
   - Handled PostgreSQL enum `application_status` safely using text casting (`status::text`) to prevent 22P02 invalid input crashes when filtering dynamic subsets.
3. Stale-While-Revalidate Caching:
   - Integrated client-side `fastCache` keyed by `admin_stats_${range}_${granularity}_${campaignId}` to deliver instant loads (<10ms) while silently revalidating data in the background.
4. Zero-Flicker Interactive UI with Recharts:
   - Built with responsive SVG charts (`ResponsiveContainer`, `AreaChart`, `BarChart`) with CSS glassmorphism, animated date switches, and CSV export capabilities.
   - Result: Response payload reduced from >25MB to <8KB, executing 11 parallel aggregations across 32,600+ users in ~450ms.
5. Canonical Demographics Bucket Normalization (Key Collision Defense):
   - When aggregating user attributes (gender, state, budget_type) containing nulls or unstructured text ('f', 'women', 'other', ''), naive SQL GROUP BY LOWER(gender) produced fragmented groups that JavaScript mapped into multiple rows with the exact same display name ('Unspecified').
   - This triggered React key collisions (key={g.name}), breaking the Next.js dev overlay.
   - Fixed by grouping directly on a canonical SQL CASE projection (GROUP BY 1), normalizing categories (Female, Male, Other, Unspecified) at the database layer, and using indexed compound keys (key={\-\}) in the UI.

[INTERVIEW STAR TAKEAWAY]
"Always push data aggregation to the database engine where B-Tree indexes, multi-core query execution, and parallel scans operate natively. Never transfer raw records to the application server or browser just to calculate counts and sums. A well-crafted SQL aggregation returning 5KB will always outperform megabytes of client-side JavaScript filtering, both in reliability and latency."

CASE 12: Meta App Review & OAuth Screencast Compliance: End-to-End Visual Verification & Reviewer Sandbox Architecture
====================================================================================================
CATEGORIES: OAuth 2.0 / Meta Graph API / Security Auditing / App Review Compliance / Screencast Architecture
INTERVIEW QUESTION: "How do you navigate third-party platform security reviews (e.g., Meta / Instagram Graph API App Review) when your production app is rejected under Developer Policy 1.6 (Screencast Not Aligned with Use Case)?"

[SITUATION]
1to7 Media submitted an App Review request to Meta for the permission `instagram_business_basic` (App ID 1569291041247830) to automate creator profile verification, follower counts, and campaign application integrity.
Meta responded with a rejection:
- "We have determined that your apps' use case is allowed, however, the submitted screencast fails to demonstrate the end-to-end experience of the use case described in the submission notes, hence the requested permission/feature is rejected."

[ROOT CAUSE INVESTIGATION]
1. Conceptual Approval vs Demonstration Failure:
   Meta explicitly approved the core use case ("apps' use case is allowed"). Rejection was 100% execution-based in the demonstration screencast and reviewer onboarding flow.
2. Missing OAuth Consent Screen in Screencast (The "Silent Token" Trap):
   In the submitted video, the test session was already pre-authenticated in Instagram. Clicking "Authorize with Instagram" caused an immediate redirect to `/dashboard` without displaying the Meta OAuth Consent Dialog ("1to7media.in is requesting access to... [Allow / Cancel]"). Meta Policy 1.6 strictly requires visually capturing the user granting permission.
3. Incomplete End-to-End Loop:
   The submission notes claimed the permission is used for: (a) creator verification, (b) dashboard stats, and (c) populating campaign application cards for brand manager review. The submitted video stopped at the creator dashboard and failed to demonstrate the data flowing into campaign applications and admin review.
4. App ID Discrepancy in Development Pipeline:
   Git commit audit revealed a reversion where the live code (`app/api/auth/instagram/login/route.ts`, `.env.vercel`, `.env.local`) defaulted to App ID `1371798394383152`, while the review submission was filed under App ID `1569291041247830`. If a reviewer attempted live testing using their assigned Meta review test user, they were greeted with authorization errors or misaligned app names.
5. Missing Context & Voiceover in Screencast:
   The video lacked English audio or captioned tooltips explaining why the intermediary mobile number step was needed (to bind the multi-tenant creator profile) before Instagram OAuth.

[SOLUTION & ARCHITECTURE]
1. Reviewer Sandbox & OTP Bypass Guarantee:
   Maintained a permanently pre-verified test user in the database (`8875912020`) that circumvents SMS OTP gateways, ensuring international Meta review bots and human reviewers in Ireland/Singapore/US never fail at the Indian telecom barrier.
2. Clean-Session OAuth Screencast Protocol:
   Before recording, revoking app permissions from Instagram Settings (`Settings -> Apps and Websites -> Remove 1to7media.in`) and using an Incognito desktop browser. This forces the browser to render:
   - Full URL bar showing `users.1to7media.in/login` transitioning to `instagram.com/oauth/authorize`.
   - The authentic Meta Consent Dialog showing the exact requested scope (`instagram_business_basic`).
   - The explicit click on the "Allow" button.
3. Complete End-to-End Lifecycle Demonstration:
   Extended the video to a structured 3-part walkthrough:
   - Part 1: Meta Login & Permission Grant (OAuth prompt -> Allow).
   - Part 2: Creator Dashboard Population (Verified handle, profile photo, follower count loaded from Graph API `/me`).
   - Part 3: Downstream Business Value (Creator applies to a brand campaign -> Verified follower count and profile auto-populate on the application card -> Brand admin reviews authentic creator metrics).
4. Synchronized Environment App ID:
   Ensured production environment secrets and OAuth endpoints strictly match the Meta App Review ID (`1569291041247830`).

[INTERVIEW STAR TAKEAWAY]
"Third-party platform reviews (Meta, Google, Apple) evaluate not just security policy, but reproducible visual proof. Even when an API use case is 100% compliant, automated and human reviewers will reject submissions if the screencast skips the OAuth consent screen due to cached browser cookies, or if downstream data utilization isn't demonstrated end-to-end. Preparing an incognito-recorded walkthrough with English on-screen annotations and zero-OTP reviewer sandbox accounts is standard engineering hygiene for enterprise social integrations."

CASE 13: React Rules of Hooks Order Violation & Production Client-Side Exception (Early Return before useMemo)
====================================================================================================
CATEGORIES: Frontend / React 19 / Next.js / Lifecycle & State Machine / Debugging
INTERVIEW QUESTION: "Tell me about a high-priority production bug where a page threw 'a client-side exception has occurred' only in production or after loading data, and how you tracked down the root cause."

[SITUATION]
Admins navigating to specific campaign applications pages (e.g. `/admin/applications/[campaign_id]`) encountered a total page crash:
- In production (`users.1to7media.in`): White screen displaying "Application error: a client-side exception has occurred while loading users.1to7media.in (see the browser console for more information)."
- In development (`localhost:3000`): Red error overlay "React has detected a change in the order of Hooks called by AdminApplicationsPage. Rendered more hooks than during the previous render. (453:32) @ AdminApplicationsPage".

[ROOT CAUSE]
1. Violation of the Golden Rule of Hooks ("Only Call Hooks at the Top Level"):
   In `app/admin/(panel)/applications/[campaign_id]/page.tsx`, an early return was inserted right in the middle of hook declarations:
   ```tsx
   if (loading) {
     return <GlobalLoader text="Loading Applications..." />
   }

   const uniqueBatches = useMemo(() => { ... }, [applications])
   ```
2. Render Hook Count Mismatch:
   - Initial Render (`loading = true`): React called hooks 1 through ~30 (useState, useEffect, context), then hit `if (loading) return <GlobalLoader />`. The `useMemo` hook at line 453 was never executed.
   - Subsequent Render (`loading = false`): After `fetchApplications()` completed, `setLoading(false)` triggered a re-render. With `loading = false`, execution passed line 450 and called `useMemo()`.
   - React detected an unexpected 31st hook during re-render that did not exist on the initial render, triggering an immediate fatal crash: `Rendered more hooks than during the previous render`.

[SOLUTION & ARCHITECTURE]
1. Strictly Unconditional Hook Placement:
   Moved all hooks (`useMemo`, `useCallback`, `useEffect`, `useState`) to the top of the component body, strictly preceding any conditional branching or early returns:
   ```tsx
   // 1. All hooks declared unconditionally at top level
   const uniqueBatches = useMemo(() => { ... }, [applications])

   // 2. Early return strictly after all hooks
   if (loading) {
     return <GlobalLoader text="Loading Applications..." />
   }
   ```
2. Safe Route Parameter Resolution with `useParams`:
   Replaced dynamic Promise unwrapping `use(params)` with the officially recommended synchronous `useParams<{ campaign_id: string }>()` hook from `'next/navigation'`, preventing potential Promise suspension inconsistencies across Next.js client-side transitions.

[INTERVIEW STAR TAKEAWAY]
"React hook calls rely on an internal linked list whose indices must match identically on every single render pass. Placing an early return (such as an auth or loading guard) before a `useMemo` or `useEffect` causes React to observe differing hook counts between states, resulting in a fatal 'client-side exception' in production. Always ensure that all hooks are declared unconditionally at the very top of the function component before any conditional early returns."

[SITUATION]
Creators discovering campaigns via public links or social media on `users.1to7media.in` faced an aggressive authentication roadblock.    - Associate the new application directly with the existing `user_id`.
   - Prevent account takeover: Do NOT return sensitive PII or grant auth session cookies to the unauthenticated client.
   - Enforce campaign eligibility (follower thresholds, location, ghosting locks, and duplicate prevention: `applications.user_id + campaign_id` unique check).
   - Trigger transactional confirmation email to the creator's registered email address.
3. Post-Submission Authentication Upsell:
   On the modal success screen, creators see: "Application Submitted Successfully! 🎉 Log in with your mobile number to track application review status and chat with the brand." with a seamless redirect to `/login`.

[INTERVIEW STAR TAKEAWAY]
"Balancing conversion velocity with identity security in consumer marketplaces requires deferring authentication friction. By adopting a 'Guest Checkout with Post-Submission Identity Claim' architecture, platforms eliminate the #1 source of top-of-funnel drop-off without exposing user accounts or issuing unverified session tokens."

CASE 16: Silent Schema Drift & 500 API Crash on Phantom Column (u.profile_photo vs u.instagram_profile_pic)
====================================================================================================
CATEGORIES: Database / PostgreSQL / API Resiliency / Schema Drift / Next.js
INTERVIEW QUESTION: "How do you handle schema drift between TypeScript models and actual database schemas that cause 500 errors in raw SQL queries?"

[SITUATION]
Upon deploying the centralized Ghosted Creators Hub (/admin/ghosted), the admin interface failed with a red banner toast "Failed to load ghost records", while the dashboard displayed zero records across all metrics despite verified active ghosted records in the database.

[ROOT CAUSE]
1. TypeScript interfaces on the client side (ActiveGhostedItem, GhostEventItem, and legacy user schemas) defined avatar images as profile_photo?: string.
2. However, in the underlying PostgreSQL database schema for public.users, the actual avatar image column is named instagram_profile_pic (there is no profile_photo column in the physical table).
3. The new API route /api/admin/ghosted/route.ts executed a raw SQL query with explicit column projections: SELECT u.profile_photo, u.instagram_profile_pic FROM public.users u.
4. PostgreSQL immediately rejected the query with error code 42703: column u.profile_photo does not exist, throwing a 500 Internal Server Error back to the client.
5. In addition, the frontend fetch threw a generic error "Failed to load ghost records" without extracting the backend error payload, hiding the root cause in the UI.

[SOLUTION & ARCHITECTURE]
1. SQL Projection Rectification with Column Aliasing:
   - Updated the query projection in /api/admin/ghosted/route.ts:
     u.instagram_profile_pic as profile_photo, u.instagram_profile_pic
     and for audit events:
     u.instagram_profile_pic as creator_photo
   - This preserved complete backwards compatibility with all existing frontend UI components expecting profile_photo or creator_photo, while referencing only columns physically present in PostgreSQL.
2. Resilient Error Propagation on Client:
   - Updated the client fetchData in app/admin/(panel)/ghosted/page.tsx to safely extract const data = await res.json().catch(() => ({})) and surface data?.error || Failed to load ghost records (${res.status}), ensuring diagnostic visibility in staging and production.
3. Verification via Direct Database Probe:
   - Validated the queries against the live Postgres instance, confirming successful return of active ghosted records (Vishakha Khatri Ahuja, campaign MyFitness F10023C201, with full reason and proof image URLs).

[INTERVIEW STAR TAKEAWAY]
"Raw SQL projections in high-performance endpoints give immense performance benefits over ORMs, but they bypass compile-time schema checking. When schema drift occurs (such as TypeScript models expecting profile_photo while PostgreSQL uses instagram_profile_pic), explicit aliasing in the SELECT clause (col as model_prop) provides zero-overhead schema reconciliation without requiring risky database migrations on high-traffic production tables."

CASE 17: Multi-State Governance Action Collision & CSS Flexbox Reverse Overflow (Approve/Reject Overlay Disaster)
====================================================================================================
CATEGORIES: Frontend / CSS Grid & Flexbox / Dual-Admin Governance / UI Architecture / Next.js
INTERVIEW QUESTION: "Describe a front-end rendering bug where multi-state conditional rendering and flexbox alignment combined to cause severe visual overlap of critical action buttons."

[SITUATION]
In the campaigns administration dashboard (`/admin/campaigns`), a new high-density List View was introduced alongside the standard Card View. When viewing campaigns in "Pending Approval" state under the dual-admin peer review system, the "Review", "Approve", and "Reject" buttons unexpectedly rendered directly on top of the "Status & Governance" column, overlapping and occluding the "Pending 2nd" badge, assigned POC names, and the modification "Diff" button.

[ROOT CAUSE]
1. Conditional Branch Leaking:
   In the list row's Actions column, the conditional check only toggled between `Approval Actions` and `Live Toggle`. The remaining standard buttons (`Edit`, `Duplicate`, `CSV Export`, `View Applications`, and `Delete`) were rendered unconditionally outside the ternary. For pending campaigns, this resulted in 8 action buttons rendering simultaneously in a single horizontal row.
2. CSS Flexbox Reverse Overflow with `justify-end`:
   The Actions column was constrained within a 12-column grid cell (~280px). The 8 buttons required over 480px of horizontal space. Because the container used `display: flex; justify-content: flex-end;`, overflowing items did not push outside the right margin; instead, they anchored to the right boundary and overflowed backwards to the left by ~200px.
3. Track Invasiveness in Fractional Grids:
   Without explicit grid column track boundaries or overflow constraints (`min-w-0`), the backwards-overflowing flex items floated directly over the adjacent column 4 (Status & Governance), rendering governance buttons right on top of text and diff badges.

[SOLUTION & ARCHITECTURE]
1. Strict Mutual-Exclusion of State Actions:
   - Partitioned the Actions column into mutually exclusive branches:
     - For `Pending Approval`: Render ONLY high-priority governance controls (`Review`, `Approve`, `Reject` or `Awaiting 2nd`), plus baseline `Edit` and `Delete`. Unapproved campaigns cannot be made live, duplicated, or exported to CSV (0 live applicants), eliminating 3 redundant buttons.
     - For Non-Pending Campaigns: Render standard operational actions (`Live/Offline` or `Launch`, `Edit`, `Duplicate`, `CSV`, `Applications`, `Delete`).
2. Robust Explicit CSS Grid Layout:
   - Replaced fragile 12-fraction tracks (`grid-cols-12`) with explicit, proportional template columns:
     `gridTemplateColumns: '145px minmax(180px, 1.4fr) minmax(150px, 1fr) minmax(165px, 1.1fr) auto'`
   - Track 1 (Rank & Sequence): 145px fixed.
   - Track 2 (Brand & Platform): Responsive fraction (expands with viewport).
   - Track 3 (Category & Metrics): 150px minimum.
   - Track 4 (Status, Governance & POC): 165px minimum, preventing any status wrapping.
   - Track 5 (Quick Actions): `auto` with `min-w-0`, guaranteed by CSS Grid boundaries to never physically cross into Track 4.
3. Enhanced Viewport Min-Width:
   - Set table container to `min-w-[1200px]` with smooth horizontal scroll for small laptops, ensuring zero button clipping or text crushing across all display sizes.

[INTERVIEW STAR TAKEAWAY]
"Flexbox containers with `justify-content: flex-end` have an insidious failure mode: when content overflows, it extends to the left rather than the right. If the preceding sibling elements lack strict CSS grid track separation, overflowing buttons visually mask previous columns. Structuring action buttons with strict mutual exclusivity based on lifecycle state and backing them with explicit CSS Grid tracks prevents visual collisions entirely."

CASE 18: Dynamic Multi-Campaign Bulk Import Template Engine & Schema Drift
====================================================================================================
CATEGORIES: Full-Stack / Data Ingestion / Dynamic Schemas / CSV Engineering / Next.js / PostgreSQL
INTERVIEW QUESTION: "How do you design an enterprise bulk import and CSV template generation system that must adapt dynamically to polymorphic entity schemas without breaking production workflows?"

[SITUATION]
Operations and campaign managers at 1to7 manage dozens of diverse influencer campaigns simultaneously (e.g. Plum, Origami, Lavie, Amazon, Myntra). Each campaign has unique creator intake requirements:
1. Custom Creator Questions: Specific application fields configured by brand managers (e.g., "Delivery Pincode", "Date of Birth", "Shoe Size", "Are you from North India?").
2. Dynamic Order Verification: Shipping address and order verification questions (e.g., "Order ID", "Shipping Address", "City", "State").
3. Budget-Type Polymorphism: Paid campaigns demand financial reconciliation columns ("Agreed Commercial", "Bank Account Number", "IFSC Code", "Account Holder Name"), whereas Barter campaigns require zero banking info.

When managers tried to bulk-import hundreds of creators for a selected campaign on `/admin/import`, clicking "Download Template" yielded a static, generic CSV that:
- Failed to include ANY of the selected campaign's custom intake questions.
- Unconditionally demanded bank account numbers and agreed commercial figures for Barter campaigns (such as Plum).
- Led to manual column reconciliation errors, uncollected creator responses, and data rejection in production.

[ROOT CAUSE INVESTIGATION]
1. Phantom Property Schema Drift:
   In the frontend template generator (`app/admin/(panel)/import/page.tsx`), the code attempted to access `camp.custom_fields`:
   `if (Array.isArray(camp.custom_fields) && camp.custom_fields.length > 0) { ... }`
   However, the database schema (`campaigns` table) and backend API route (`/api/admin/campaigns/[id]`) store dynamic custom questions in the JSONB column `form_fields` (and order questions in `order_form_fields`), not `custom_fields`. Because `camp.custom_fields` was undefined, the template generator silently skipped all custom campaign fields.
2. Hardcoded Commercial Bias:
   The generator unconditionally pushed commercial banking headers (`'Agreed Commercial'`, `'Bank Account Number'`, `'IFSC Code'`) onto the CSV header array without checking `camp.budget_type`. For Barter campaigns, this confused brand POCs and creators.
3. Static Placeholder Sampling:
   Custom field sample rows contained hardcoded generic strings (`'Sample Response'`) instead of utilizing the rich option sets already defined in the campaign configuration (e.g. dropdown options like "Yes" / "No", or city/state targeting lists).
4. UTF-8 BOM Absence:
   The generated CSV blob was exported without a UTF-8 Byte Order Mark (`\uFEFF`), which caused Excel on Windows systems to misinterpret accented characters or regional Indian script when opened by operations teams.

[SOLUTION & ARCHITECTURE]
1. Polymorphic Campaign Schema Resolver:
   - Built a dynamic schema inspector that queries `/api/admin/campaigns/[id]` and normalizes:
     - `camp.form_fields`: Custom application questions configured in the campaign builder.
     - `camp.order_form_fields`: Shipping and order fields when `camp.order_form` is true.
     - `camp.payment_form_fields`: Post-approval deliverable verification requirements.
2. Context-Aware Budget & Banking Columns:
   - If `camp.budget_type` contains 'Paid': Include 'Agreed Commercial', 'Bank Account Number', 'IFSC Code', 'Account Holder Name', and 'Partial Payment' (if `partial_payment_enabled` is true).
   - If `camp.budget_type` contains 'Barter': Intelligently omit banking fields to maintain a clean, barter-focused data intake structure.
3. Realistic Sample Row Generation:
   - For dropdown fields (`field.type === 'dropdown'`), populate sample rows with `field.options[0]`.
   - For date and number fields, provide syntactically valid dates (`YYYY-MM-DD`) and numerals.
   - For location and demographic targeting, seed sample values from `camp.target_states`, `camp.target_cities`, and `camp.gender_required`.
4. Robust File Generation & Encoding:
   - Prefix the Papa.unparse CSV output with `\uFEFF` (UTF-8 BOM) for flawless cross-platform Excel and Google Sheets compatibility.
   - Generate sanitized, human-readable download filenames: `Template_[BrandName]_[CampaignCode].csv`.
5. Seamless Downstream Ingestion:
   - The bulk import parser (`handleFile` and `/api/admin/import`) automatically captures unmapped campaign-specific headers into the `applications.form_data` JSONB column, where they are dynamically rendered in the `/admin/applications/[campaign_id]` portal without requiring table schema migrations.

[INTERVIEW STAR TAKEAWAY]
"When engineering bulk data tools for polymorphic domain entities, client-side template generators must never rely on static assumptions or unverified property names. Always synchronize the generator against the single source of truth—the database JSONB schema (`form_fields` vs `custom_fields`) and entity metadata (`budget_type`). Back the output with UTF-8 BOM encoding and intelligent sample defaults so operations teams can immediately work with clean, pre-validated spreadsheets."

CASE 19: Question-Text-as-Key Drift: Renamed Campaign Questions Silently Orphan Answers
====================================================================================================
CATEGORIES: Data Modeling / JSONB Schema Design / Filtering Correctness / Product Analytics
INTERVIEW QUESTION: "Tell me about a time a seemingly simple feature request exposed a hidden data-modeling flaw."

[SITUATION]
The ops manager asked for per-question filters on the Applications page (e.g. "show HRX applicants whose quoted commercial for 1 Reel + 1 Story is <= 3500"). Before building it, we audited production data for the HRX campaign (35 applications).

[ROOT CAUSE]
1. Campaign questions live in `campaigns.form_fields` (JSONB array of {name, type, options}). Creator answers live in `applications.form_data` (JSONB) keyed by the question's display TEXT, e.g. form_data["please share your best commercials for 1 Reel + 1 Story ..."] = "3500".
2. Questions have no stable ID. When the brand team edited the wording mid-campaign ("If not, please share your best commercials..." -> "please share your best commercials..."), every earlier answer stayed under the OLD key.
3. Audit result: only 9/35 applicants have an answer under the current question text; 24/35 (69%) answered the old wording. A naive filter on the current name would silently hide the majority of applicants, i.e. a cheaper creator could be excluded from shortlisting without anyone noticing.
4. Secondary data-quality issues: numeric answers stored as strings with junk values ("1"), free-text inconsistency ("Bengaluru" / "Bangalore" / "bangalore"), dropdown case drift ("yes" vs "Yes"), and a status value ("Approved") leaking into a city column from a mis-mapped CSV import.

[SOLUTION & ARCHITECTURE]
1. Introduce a stable field identity: each form field gets an immutable `id` plus an `aliases[]` list of historical question texts. Readers resolve an answer via id -> current name -> aliases. Fully additive JSONB change, zero migration, no rewrite of historical rows.
2. Builder auto-detects orphaned form_data keys for the campaign and offers one-click "link as previous wording" so renamed questions keep their history.
3. Per-question `filterable` toggle in the campaign builder; the Applications page renders type-aware filters (number range with tolerant parsing of 5k / Rs 5,000, dropdown multi-select with case-insensitive matching, grouped distinct values for text, date/age range) only when exactly one campaign is selected.
4. An "Unparseable / Not answered" bucket is always shown so nothing is silently dropped.
5. CSS Stacking Context & Backdrop-Blur Z-Index Elevation: Dynamic question popovers are isolated in high z-index stacking contexts (`relative z-30` on container, `z-[60]` on active trigger, and `z-[100]` on the floating modal with backdrop-blur-2xl) so popups float cleanly over table headers and backdrop-filtered containers without getting clipped or trapped underneath.

[INTERVIEW STAR TAKEAWAY]
"Never key user data by mutable display text. Before shipping a filter, measure coverage against real production rows: our audit showed a filter on the current question would have hidden 69% of applicants. Stable IDs plus alias resolution fixed it additively, with no risky data migration."

CASE 20: Cross-Entity Location Cascade Disconnect: Unbound State-to-City Dropdowns Corrupt Profile Sync & Eligibility
====================================================================================================
CATEGORIES: Frontend Architecture / Dynamic Form Engine / State Machine / Data Hygiene / Geographic Validation
INTERVIEW QUESTION: "Tell me about a subtle form design flaw that caused data corruption across connected database tables, and how you architected a cascading dependency engine to eliminate it."

[SITUATION]
During campaign applications (e.g. Plum campaign CAM-MVF425OZ), creators encountered custom questions for "STATE / UT" and "CURRENT CITY". A creator was able to select "ASSAM" as their state, but the city dropdown listed "Kolkata" (the capital of West Bengal). The creator submitted the application with this geographically impossible pair ("Assam" + "Kolkata").
Downstream, this corrupted data propagated into two critical systems:
1. Creator Profile Sync: The application submission endpoint (/api/apply -> extractProfileUpdatesFromFormData) automatically synced the submitted form answers into the users table (users.state and users.city), permanently polluting the creator's profile.
2. Campaign Eligibility & Logistics Targeting: When subsequent campaigns checked location eligibility (via checkCampaignLocationEligibility for state-exclusive or city-exclusive campaigns), users with mismatched states and cities triggered false negatives or bypassed geo-fences, while brand operations teams faced delivery dispatch failures due to invalid destination hubs.

[ROOT CAUSE]
1. Decoupled Static Dropdown Rendering:
   In the campaign question builder (FormFieldBuilder.tsx), when an admin created a "Current City" question, the system defaulted field.options to TOP_METRO_CITIES (18 top tier-1 metro cities across India, including Kolkata, Delhi, and Mumbai).
2. Missing Cascading State Machine in Application Modals:
   In CampaignDetailModal.tsx (the primary creator dashboard application modal), custom campaign questions (campaign.form_fields) were rendered blindly as independent Select inputs. The city Select component rendered field.options without any dependency or reference to what the creator had selected in the "STATE / UT" field.
3. Zero Reactive State Resetting:
   Even if a user changed their state, the city field retained its previously selected value. There was no reactive listener to reset dependent child fields upon parent state transition.
4. Total Absence of Cross-Field Boundary Validation:
   Neither the client-side pre-submit requirement checker (getPendingCustomRequirements) nor the submit handlers checked whether the chosen city actually belonged to the selected state (INDIA_DATA[state]).

[SOLUTION & ARCHITECTURE]
1. Canonical Domain Classification & Utilities (lib/utils/location-utils.ts):
   - Implemented regex-based classification functions:
     * isStateField(name, syncKey): Accurately detects state questions across arbitrary naming schemes ("State / UT", "Current State", "Select State", profile_sync_key === 'state').
     * isCityField(name, syncKey): Accurately detects city questions ("Current City", "City / District", profile_sync_key === 'city').
     * isCityInState(city, state): Cross-checks city against the canonical INDIA_DATA dictionary of 36 Indian States/UTs and their official districts.
2. Profile Sync Regex Normalization (lib/utils/profile-sync-utils.ts):
   - Expanded CANONICAL_FIELDS.state patterns to match "State / UT" and case variations to guarantee accurate profile synchronization.
3. Reactive Cascading Form Engine in Application Modals (CampaignDetailModal.tsx & ApplicationFormModal.tsx):
   - Created a centralized, unified field renderer (renderCustomFormField) supporting both inline profile completion and custom campaign questions.
   - Enforced State-First Dependency: The city Select input is strictly disabled (disabled={!activeState}) until the user selects a State, displaying a descriptive placeholder ("First select State / UT above").
   - Dynamic District Projection: Upon state selection, city options dynamically project from INDIA_DATA[activeState] (e.g. selecting "ASSAM" dynamically loads all 33 Assam districts: Kamrup Metropolitan, Dibrugarh, Silchar, Jorhat, etc.).
   - Visual Feedback Badge: Added an informative indicator below the city selector (e.g. "📍 Showing 33 cities in ASSAM") confirming the dynamic filter to the user.
   - Auto-Eviction State Machine: When a creator changes the state, the form state machine inspects the dependent city. If the current city does not exist in the new state's district list, it is instantly wiped clean (formData[cityName] = '').
4. Dual-Gate Cross-Entity Validation:
   - Client Submission Gate: getPendingCustomRequirements and handleSubmit run isCityInState(city, state) and reject invalid combinations with a descriptive notification before the network request is initiated.
   - Backend Defense: /api/apply ensures profile sync rejects invalid geographical pairings, preventing database corruption.

[INTERVIEW STAR TAKEAWAY]
"When building dynamic, form-driven platforms, hierarchically dependent entities (such as State and City) must never be modeled as independent, unconstrained dropdowns. A robust form engine must implement reactive cascading: child inputs must remain disabled until parent constraints are satisfied, child options must dynamically project from the parent entity's dictionary (INDIA_DATA[state]), stale child selections must be automatically evicted upon parent state changes, and cross-field boundary validations must guard both client submission and database ingestion."
